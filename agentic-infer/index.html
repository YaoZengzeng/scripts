先看问题 / 为什么 Agent 不一样

请求是一瞬间，任务是一整条链

一轮“想一想 → 调工具 → 再想一想”，会反复携带已有上下文。

  • 多轮重复读系统提示、工具定义与历史反复出现；KV 缓存就像“读过材料后留下的笔记”。
  • 等待与突发交替工具执行时模型暂歇；子 Agent 并行启动时，请求又会集中涌入。
  • 最后一步决定体验多条分支需要汇合，最慢的关键分支可能拖住整个任务。
优化目标在任务质量不下降的前提下，缩短完成时间，降低每个成功任务的成本。
依据：Dynamo · Full-Stack Optimizations for Agentic Inference

优化 01 / 接入层 已支持 + 应用侧实践

统一请求结构，保持前缀稳定

像整理一份档案：固定资料放前面，每次只把新进展追加在后面。

  • 让不同 Agent 接入同一平台Dynamo 提供 Chat Completions、Responses、Messages 接口，适配文本、工具调用和推理内容。
  • 把“固定”与“变化”分开应用侧稳定系统提示、工具定义及其顺序；避免把时间戳等变化字段放在公共前缀开头。
  • 稳定的是 token 前缀，不只是意思换模板、重排工具或改写历史都可能减少命中；语义相似不等于缓存可复用。
收益减少协议适配摩擦，也为后续路由与缓存复用打好基础。
依据：多协议支持 · 前缀组织为应用侧建议，不代表平台自动改写提示词。

优化 02 / 请求信号 已支持 · 按需启用

让平台知道：这次要忙多久

Agent 掌握任务意图，推理平台掌握资源；用轻量提示把两端连接起来。

  • 预估输出长度：osl短查询与长报告对资源的占用不同。告诉路由器预计生成多少 token，有助于资源估计。
  • 附带重要性与预热意图priority 表示优先级；speculative_prefill 请求下一轮前缀预热，后面分别展开。
  • 估计要用真实反馈校准按任务类型统计实际输出长度，逐步修正；提示是估计，不是完成时限或资源保证。
收益不再把“生成一句话”和“写一份报告”当成同样大小的工作。
依据：NVIDIA Request Extensions · Agent Hints

优化 03 / KV 感知路由 已支持 · 需缓存信息

把请求交给“读过材料的人”

负载均衡不只是“哪台空闲”，还要看“哪台已经有这段上下文”。

  • 维护缓存位置索引路由器根据 worker 的 KV 信息，判断各节点能复用多少输入前缀。
  • 同时算缓存账与排队账缓存命中可减少 Prefill；但节点太忙时，换一台可能更快，不能只追求命中率。
  • 让长会话持续受益工具返回后的下一轮尽量复用已有历史，而不是在另一台 GPU 上重新“读全文”。
选择原则综合等待、补算和生成负载，尽量缩短实际响应时间。
依据：KV-Aware Placement · 源码：KV Router

优化 04 / 跨层优先级 依赖队列策略与后端配置

让关键路径先走一步

用户正等着的分支，不应始终排在后台批处理之后。

  • Agent 标注“谁更重要”用 priority 传递重要性，Dynamo 对外统一为数值越高越重要，并转换各后端的语义。
  • 路由排队与引擎排队一起考虑启用匹配的路由队列策略及引擎优先级调度，避免前一站加急、后一站又普通排队。
  • 不要把加急当成无限插队为普通流量保留服务空间，观察尾延迟；优先级不等于抢占所有正在运行的请求。
边界当前 FCFS / WSPT 队列可利用 priority；EDF 按截止时间排序，不因该提示重排。
依据：priority 与后端要求 · 路由队列配置

优化 05 / 场景化路由 策略可配置 / 可扩展

不同的 Agent，不必走同一条路

先用通用策略建立基线，再针对真实瓶颈定制，而不是一开始就上复杂算法。

  • 长会话：关注亲和性尽量回到已有上下文的节点；同时考虑节点故障、容量不足和热点问题。
  • 并行子任务：关注分散与共享避免所有子 Agent 堆在同一节点；让负载分散，同时尽可能复用公共前缀。
  • 超长上下文：先确认能装下把 KV 容量和输出长度纳入决策；必要时自定义筛选与评分，再比较效果。
实施建议通过策略配置或扩展接口落地；在线学习路由是可选方案，不是默认能力。
依据：Agentic Workload Routing Strategies · 源码：策略扩展

优化 06 / 下一轮预热 已支持 · 需显式启用

等工具时，先准备下一轮

利用已有信息预热可预测前缀，把一部分准备工作从关键路径上移走。

  • 当前回复结束后开始准备speculative_prefill 让平台根据已完成的对话构造下一轮前缀，提前做预填充。
  • 工具返回后接着处理新增内容若实际请求前缀兼容且缓存还在，就不必等下一轮到达后才做全部准备。
  • 只预热可预测、值得预热的部分未知工具结果不能提前算；预热错误会浪费算力，高负载时需要限制额外工作。
不要混淆这里是提前计算前缀，不是投机解码；也不等同于把远端 KV 自动预取回 GPU。
依据：speculative_prefill · 源码：下一轮预热实现

优化 07 / 分层缓存 依赖引擎与存储集成

显存是书桌，不是整座图书馆

把暂时不用的上下文搬到更便宜的存储层，为正在执行的请求腾出空间。

  • 热数据放近，冷数据放远GPU 显存承接活跃计算，CPU 内存及本地存储承接更多历史；共享存储进一步扩展容量。
  • 工具等待期是下沉窗口不必让所有暂停会话一直占满显存；恢复时在搬回与重算之间权衡。
  • 路由要看缓存在哪一层显存命中与磁盘命中的代价不同。命中不代表零等待，传输带宽也会成为瓶颈。
能力边界四层是参考架构，不是默认全部连通；按返回时间主动预取的通用钩子，原文仍列为演进方向。
依据：分层 KV 架构 · 分层命中权重

优化 08 / 跨节点复用 集成能力 · 非默认保证

公共材料，不必每人抄一份

多 Agent 扩散的不应只是请求，还应包括“已经算过的公共上下文”。

  • 复用真正相同的公共前缀主 Agent 与子 Agent 共享的系统提示、工具定义，可成为跨 worker 复用的候选。
  • 从“只找本地”走向“查到后搬过来”集成共享缓存或节点间传输后，可用加载代替重复 Prefill；路由需计入搬运成本。
  • 先确认兼容与隔离模型、KV 格式、连续前缀与访问域必须兼容；不同租户不能为了命中率随意共享。
判断门槛加载时间小于重算时间时才值得搬；NIXL 是传输组件，不会自动把所有缓存变成共享池。
依据：共享 KV · 源码：共享命中描述 · 缓存隔离

优化 09 / 按价值保留 部分支持 · 细粒度接口演进中

不是最近用过的，就最值得留下

“刚刚生成”与“马上还会用”是两件事，单纯按最近使用时间淘汰并不够。

  • 把显存留给高复用价值的内容系统提示和公共工具定义往往多轮复用；暂停中的重要长会话也值得适当保护。
  • 今天先用请求级优先级SGLang 在启用相应淘汰策略后可利用 priority；不能假设所有后端行为一致。
  • 更细的控制仍需区分层次Token 区间保留、TTL 与跨存储层生命周期，不等于已有统一的 Dynamo 请求 API。
明确限制不要把 nvext.cache_control 当成可用的 TTL 锁定接口；当前不是这套语义。
依据：Selective Cache Retention · 当前后端支持边界

优化 10 / 生命周期感知 原文探索方向 · 非通用现成功能

Agent 已经结束，缓存也该知道

从“只看一次请求”走向“知道会话何时暂停、恢复、收尾”。

  • 子 Agent 结束：回收私有临时 KV若后续不再使用其完整历史，可降低保留价值，避免无意义的存储写入。
  • 历史压缩：旧上下文退场摘要替代长历史后，旧 KV 不应继续按“活跃会话”长期保护；新摘要前缀可能需要重算。
  • 公共前缀不能跟着一起删回收必须考虑其他 Agent 是否还在引用，避免一个分支退出影响整个任务。
演进方向将会话事件与缓存保留、淘汰、下沉连接起来；已有会话标识或亲和性不等于生命周期回收。
依据：Agent Lifecycle Awareness

优化 11 / 分离 Prefill 与 Decode 已支持 · 按负载选择

读长材料与写答案，各用合适的资源

避免一个超长输入，让正在生成答案的其他请求一起停下来等。

  • Prefill 池：集中处理输入承担长上下文与冷缓存补算，关注首字等待和输入处理能力。
  • Decode 池：稳定输出 token关注生成间隔和并发会话的 KV 容量，两类资源可以独立调整。
  • 通过高效传输连接两池以 NIXL 等后端传输路径移动 KV，减少搬运开销；通信仍然有成本。
取舍低并发、短输入或高缓存命中时，聚合部署可能更划算；不要为“分离”而分离。
补充依据：Disaggregated Serving · 部署示例

优化 12 / 资源弹性 Planner 已支持 · 需指标与配置

按瓶颈扩容，不只盯着 GPU 利用率

排队太久、生成变慢、缓存装不下，是三种不同的求救信号。

  • 用服务目标驱动容量Planner 可结合流量预测、性能模型及运行指标，围绕首 token 时间和生成间隔调整副本。
  • 把容量加到真正吃紧的地方输入处理堵塞关注 Prefill；生成或 KV 容量吃紧关注 Decode，而不是整组同比例放大。
  • 扩缩容也要考虑缓存温度新节点是冷的，缩容可能丢掉热缓存；需预留启动时间、平稳迁移并观察恢复成本。
边界Planner 主要优化推理服务指标；成功率、工具等待和完整任务时间仍要由应用侧联合评估。
补充依据与源码入口：Dynamo Planner · SLA-driven autoscaling
