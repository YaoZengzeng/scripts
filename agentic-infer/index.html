一个问题，三层协同

Agent 的上下文，为什么会被反复重算？

以编码 Agent 为例：读仓库 → 调工具 → 修改代码 → 执行测试。每轮新信息不多，却不断携带已有历史。

  • 多轮复用：输入长，增量相对小系统提示、工具定义与对话历史形成可复用前缀。原文 42 次调用样本的缓存读写比约 11.7，体现“写一次、读多次”。
  • 暂停与分叉：上下文不再跟随计算工具等待时前缀可能被淘汰；子 Agent 落到其他 worker 时公共前缀又要重算；分支结束后私有 KV 却仍占空间。
  • Dynamo 的职责：把 Agent 意图接到推理系统Harness 管任务与工具；Dynamo 负责请求接入、路由与缓存协同；vLLM / SGLang / TRT-LLM 执行模型并管理引擎 KV。
沿链路展开先让请求携带语义，再选对 worker，最后决定 KV 如何共享、保留、预取和回收。
主线与术语：Agentic Inference · 引言。Prefill 处理输入并构建 KV；Decode 基于 KV 逐步生成。

01 FRONTEND / 多协议与内容结构 已支持

接住交错的思考、工具调用与文本

问题：Agent 的一次回复不是单一文本；模型与框架对 reasoning、tool call 的表达不同，转换不当会破坏下一轮历史。

  • 多协议归一到共同的处理链路Dynamo 接入 Chat Completions、Responses、Messages；后两者的类型化内容块更直接表达交错输出，前者也支持独立工具调用字段。
  • 保留内容边界，配套模型解析器前端与 parser 将模型输出还原为工具调用、推理与文本；正确处理调用标识和工具结果，Harness 才能可靠继续执行。
  • 让下一轮的稳定前缀保持一致应用侧稳定 tool schema、顺序及模板参数；思考块是否保留按模型模板处理，避免本可复用的历史因渲染变化失配。
收益与边界内容结构为后续策略提供依据，但“能识别内容块”不代表已自动按块类型实施缓存保留。
原文：Layer 1 · Multi-Protocol Support。稳定前缀属于应用侧协同实践。

01 FRONTEND / Harness–Orchestrator 接口 Agent Hints 已支持

把 Agent 知道的事，告诉推理平台

问题：Harness 知道哪条分支正在阻塞任务、下一次是短查询还是长综合，但服务端通常只看见匿名 token 请求。

  • priority：表达关键路径的重要性为用户正在等待的分支赋予更高优先级，经 Dynamo 传到路由与引擎；数值越高表示越重要。
  • osl：预估输出长度，改善负载判断按工具调用或任务类型预测生成 token 数；它是负载估计，不是 max_tokens。输出块跟踪启用后可进一步利用生成进度。
  • speculative_prefill：声明下一轮预热意图当前回复完成后，提前计算可预测的下一轮前缀；后文结合工具等待说明它与跨层 KV 预取的区别。
接口边界提示不是资源保证，也不能表达所有生命周期事件；会话身份通过请求头传递，不放进 agent_hints。
原文：Agent Hints · 行为核对：nvext 参考

02 ROUTER / KV-Aware Placement 已支持 · 需缓存信息

下一轮请求，尽量命中上一轮上下文

问题：Agent 每轮只增加少量工具结果；无缓存感知的分发却可能换一台 worker，把长历史重新 Prefill 一遍。

  • 先知道“哪个 worker 持有哪些前缀”worker 发布 KV 事件，Indexer 维护块 / 前缀索引；路由器对输入分块、查询各 worker 的可复用重叠。
  • 把缓存收益与活跃负载一起评分命中前缀抵扣未缓存 Prefill 工作量；同时计入活跃 Prefill 与 Decode 压力，避免将所有续轮挤向同一热点节点。
  • 目标是减少实际等待，而非只提高命中率高命中但排队很长的 worker 未必最优。保留请求级负载记账，并根据工作负载调整缓存与计算的权重。
架构只需记住Indexer 保存“KV 在哪里”的元数据，worker / 存储层才持有 KV 数据；索引命中不保证数据始终可用。
原文：KV-Aware Placement · 代价模型 · 源码入口

02 ROUTER / Priority Scheduling 依赖队列策略与后端配置

让阻塞任务的分支，先获得服务

问题：主 Agent 正在等待一个工具决策或子任务结果，却与不紧急的并行探索混在同一队列中。

  • 由 Harness 标注关键分支将 priority 附到请求；Dynamo 对外统一为高值更重要，不要求 Harness 理解各引擎优先级数值方向。
  • 路由排队与引擎排队使用同一意图支持优先级的路由队列先调度重要请求，再向后端转换并透传该信号；不能只在入口加急，进入引擎后又完全忽略。
  • 策略开启与公平性需要共同考虑FCFS / WSPT 队列可利用 priority，EDF 按截止时间排序；SGLang / vLLM 等后端还需显式开启相应优先级调度。
边界优先级不等于全局严格执行顺序，也不保证抢占已运行工作；需避免后台探索长期饥饿。缓存淘汰的优先级另在第三层说明。
原文：Priority Scheduling · 行为与后端要求：priority 参考

02 ROUTER / Agentic Workload Routing Strategies 策略可扩展

串行编码、并行探索、长文研究，路由侧重不同

问题：默认的缓存与负载评分看不到完整工作流；一套权重未必同时适合长会话和大量短命子 Agent。

  • 串行多轮：优先连续复用历史编码 Agent 反复扩展同一前缀，可侧重会话亲和；但需要在故障、热点和容量压力下允许重新放置。
  • 并行 fan-out：均衡与公共前缀一起考虑子 Agent 短上下文、并发高；不能为追求同一份缓存而全部绑定到一台 worker，应结合共享能力分散负载。
  • 超长研究任务：容量约束先于偏好完整状态必须能被承载，再比较命中和负载。原文通过 KvRouter 扩展接口，引入会话信息与自定义选择逻辑。
实现入口get_potential_loads() 观察候选负载，best_worker() 查询选择，generate() 分发。NAT 在线学习路由是原文扩展示例，不是默认收益保证。
原文：Agentic Workload Routing Strategies · 策略扩展源码

03 KV CACHE / The Problem with Uniform Eviction

选对 worker 还不够：需要的 KV 可能已经没了

问题：LRU 只看最近访问；它不知道 Agent 正在等工具，也不知道刚结束的分支不会再回来。

  • 长暂停让高价值前缀变“冷”原文讨论 2–30 秒工具等待：系统提示与会话历史仍会复用，却可能在高流量下被挤出，恢复时重新计算。
  • 新生成的 KV 不一定有后续价值已结束子 Agent 的私有上下文、被摘要替代的旧历史，可能刚生成不久就失去复用价值。
  • 缓存管理要回答三个 Agent 问题下一轮去哪里取？工具返回前能否准备好？任务继续或结束时，哪些块应该保留、哪些该回收？
后续主线先让 KV 跨 worker 可用，再减少恢复时的等待，最后按复用价值与会话生命周期决定淘汰。
原文：The Problem with Uniform Eviction

03 KV CACHE / KV Cache as a Shared Resource 依赖后端与存储集成

把会话 KV，从本地临时状态变成可复用资源

问题：所有暂停会话都留在显存会挤占活跃请求；直接淘汰又会丢掉下一轮要用的前缀。

  • 通过分层存储跨越工具等待期活跃 KV 在 GPU；暂时不用的可下沉到 pinned DRAM、NVMe 或远端层。卸载释放显存，但不必放弃后续复用。
  • 原文的共享设计：按前缀身份注册块原文以 HiCache / KVBM 说明写穿与共享注册方向：KV 块按 sequence hash 去重，已注册不可变块由可访问该层的 worker 加载。
  • 索引、存储与传输三者必须配合索引回答“块在哪里”，存储提供可读副本，NIXL 等路径搬运数据；路由知道有缓存，不代表后端已经能读取它。
能力边界四层是原文参考架构，不是所有部署默认全部打通；写穿、注册和共享语义须与所用引擎及连接器核对。
原文：KV Cache as a Shared Resource · 分层与共享

03 KV CACHE / 共享解决的问题之一 需要跨 worker 共享集成

子 Agent 冷启动：公共前缀只算一次

问题：主 Agent 已算过系统提示与工具定义；多个子 Agent 落在不同 worker 后，仍各自为相同前缀重复 Prefill。

  • 把共享前缀与分支私有内容分开公共系统提示、工具定义作为共享候选；每个分支只对自己的任务、检索结果与新增历史做增量计算。
  • 先查可复用位置，再加载到目标 worker主 Agent 计算的公共块进入可访问的共享层；子 Agent 在其他 worker 上加载，而不是全部重新计算。
  • 复用必须满足连续性和兼容性以相同模型、模板及缓存域下的连续 token 前缀为前提；同样一段工具文本出现在不同前文后，不代表 KV 可以直接拼接。
优化结果把多次相同 Prefill 变成一次计算与后续加载；只节省公共部分，私有后缀与数据搬运仍有成本。
原文：共享 KV 与子 Agent 冷启动 · 连续可加载前缀的源码表示

03 KV CACHE / 共享解决的问题之二 面向 P/D 多轮的集成目标

多轮 P/D：上一轮生成的 KV 在哪里？

问题：Prefill 与 Decode 分开后，上一轮新生成的 KV 留在 Decode worker；下一轮 Prefill 却需要包含它的完整历史。

  • 单轮传输只解决了前半段Prefill worker 计算输入前缀 P，经 NIXL / 后端传输交给 Decode；Decode 继续生成内容，形成新增 KV 后缀 Δ。
  • Agent 续轮需要的是 P + Δ工具返回后，下一次输入包含上一轮回复。若目标 Prefill worker 只有 P，就仍需补算缺少的历史，无法实现完整续轮复用。
  • 将新增块纳入共享可见性与加载路径原文提出由 Decode 把新增块写入公共层，使下一轮 Prefill 能取回连续历史；新工具结果则继续增量计算。
必要架构背景这里只讨论 P/D 对 Agent 多轮 KV 归属的影响；完成 P→D 传输，不等于下一轮 D→P 的状态复用已自动打通。
原文：共享 KV 与 disaggregated serving 的多轮状态

03 KV CACHE / 工具等待中的卸载与预取 前缀预热已支持 · 跨层预取钩子演进中

工具还没返回，先准备即将使用的上下文

问题：KV 保存在低层存储，只解决了“没丢失”；若直到下一轮到达才加载，恢复延迟仍在用户等待路径上。

  • 方向：等待期间下沉，恢复前预取Harness 可利用工具耗时分布预测恢复时机，提前将已有 KV 从存储层带回 GPU；原文将通用预取钩子列为建设方向。
  • 现有机制：speculative_prefill 提前计算当前轮回复完成后重建预测前缀，渲染、tokenize，并发送 max_tokens=1 的预热请求；它计算前缀，不是指挥远端块搬运。
  • 只准备可预测且值得准备的部分未知工具结果不能提前算；模板变化、提前结束或过早加载都可能浪费资源，需要限制预热并发、超时与前台干扰。
两条路径缺少的 KV → 提前计算；已有但不在 GPU 的 KV → 提前搬运。二者都利用等待窗口，但不是同一项能力。
原文：工具等待与 Prefetch · 当前预热语义 · 预热源码

03 KV CACHE / Selective Cache Retention 请求优先级可用 · 细粒度跨层控制演进中

共享解决“拿得到”，保留策略解决“别先丢”

问题：公共前缀即使进入共享体系，也可能被低价值、刚生成的临时块挤出；单靠 LRU 仍无法保护即将恢复的会话。

  • 今天：通过请求优先级保护重要缓存nvext.agent_hints.priority 可被支持的后端用于缓存淘汰；SGLang 需启用 --radix-eviction-policy priority。
  • 设计方向：普通块与标注块区别处理原文提出未标注块走 LRU，带保留指令的块进入优先级结构；未来可把优先级、生命周期与放置意图随块传播到共享层。
  • 请求级、区间级与集群级不是同一能力TRT-LLM 的 token-range retention 是引擎原语，不等于 Dynamo 已提供统一的区间 / TTL 接口或跨集群块租约。
不要误用nvext.cache_control 不是可用的 TTL pinning 接口；兼容 Anthropic 的 cache_control 标注也不表示自托管缓存获得相同保留语义。
原文：Selective Cache Retention · 后端边界：priority 参考

03 KV CACHE / Agent Lifecycle Awareness 跨层生命周期控制属探索方向

分支结束或历史压缩后，及时回收临时 KV

问题：请求结束不等于会话结束；缓存系统也看不见“这个子 Agent 不再运行”或“旧历史已被摘要替代”。

  • 用会话事件识别 ephemeral KV子 Agent terminate、会话 compaction，以及不再进入后续输入的 thinking 内容，都可能使部分 KV 失去复用价值。
  • 回收私有后缀，避免无效下沉原文探索 session 标记与引擎语义检测：降低临时块的保留价值，优先回收，必要时跳过共享存储写入。
  • 保留仍被引用的公共块其他 Agent 可能还在使用同一前缀；回收需考虑引用与共享关系。只要历史仍参与后续 attention，就不能因“推理结束”而随意删除。
闭合生命周期公共前缀长期复用，私有临时状态及时退场；已有会话标识 / 亲和性，不等于自动拥有跨层生命周期回收。
原文：Agent Lifecycle Awareness

回到同一个编码任务 / Closing the Gap

让一次 Agent 循环，穿过三层优化

不是给平台堆更多组件，而是把 Agent 已知的上下文、依赖与生命周期，传给真正作出决策的层。

  • 请求进入：保留结构，传递意图Frontend 正确处理思考与工具调用；Harness 用 priority、osl、预热提示描述当前请求与下一轮需求。
  • 选择执行位置：续轮命中，关键分支先行Router 综合缓存与负载；串行续轮尽量复用历史，并行探索避免热点，让阻塞主任务的请求优先获得服务。
  • 状态退出：值得复用的留下，不再使用的回收共享层承接公共前缀与跨 worker 历史；工具等待可用于准备下一轮，分支终止后回收私有临时状态。
核心结论Frontend 让意图可见，Router 让已有 KV 可命中，缓存管理让有价值的状态持续可用、无价值的状态及时退出。
