背景 01 / 从无状态 API 到有状态工作流

Agentic 推理的优化单位：任务 DAG

单次 HTTP 请求是无状态接口，但多轮推理在上下文、缓存和执行依赖上高度相关。

  • 多轮依赖：递增前缀与重复 Prefill系统提示、工具定义与历史在多轮中重复输入；缓存丢失会把已完成的计算重新放回关键路径。
  • 执行结构：串行链 + 并行分支工具调用产生暂停 / 恢复，子 Agent fan-out 产生突发并发；fan-in 汇合受最慢依赖分支约束。
  • 优化指标：任务完成时间与成功成本单请求 TTFT 改善不一定缩短整个任务；需要把模型推理、工具耗时、重试和关键路径一起关联。
优化目标在任务质量不下降的前提下，缩短完成时间，降低每个成功任务的成本。
依据：Dynamo · Full-Stack Optimizations for Agentic Inference

背景 02 / 负载画像

长上下文、多轮复用与突发并发

相同的 QPS，可能对应完全不同的输入工作量、KV 占用和调度压力。

  • ISL / OSL 分布，而非只看请求数ISL 是输入长度，OSL 是输出长度。检索、代码编辑与长推理的分布不同，均值会掩盖长尾与 KV 容量压力。
  • WORM：一次写入，多次读取原文记录的 42 次 Claude Code 调用中，缓存读取约 891K token、写入约 76K token；重点是复用结构，而非绝对规模。
  • 工具等待改变缓存“热度”原文讨论 2–30 秒工具暂停；LRU 可能在 Agent 恢复前淘汰前缀，造成 resume miss 和重复 Prefill。
采样建议同时记录输入 / 输出长度、复用比例、工具等待、分支宽度和会话持续时间，保留它们之间的关联。
来源：Agentic Inference · 原文负载分析。图中数值取自该样本，不外推到其他模型与平台。

背景 03 / 项目定位

Dynamo：推理引擎之上的分布式编排层

开源、数据中心级推理框架：Rust 承担运行时与高性能组件，Python 提供后端集成与扩展。

  • 不替代 vLLM / SGLang / TensorRT-LLM引擎负责模型执行、batching、attention kernel 和本地 KV；Dynamo 把多个引擎实例组织为一个服务系统。
  • 关注跨 worker 的协调问题Frontend 接入，Router 选择目标，缓存集成与 NIXL 连接 KV 数据路径，Planner 根据服务目标调整资源池。
  • 从单机服务扩展到集群服务支持聚合式与 P/D 分离部署；在 Kubernetes 上由 Operator 管理部署资源，Planner 提供副本数决策。
适用边界单 GPU、低并发场景可能只需推理引擎。Dynamo 的主要价值在跨节点路由、状态复用和资源协同。
依据：Dynamo 项目定位 · 系统架构

背景 04 / 请求路径与通信平面

请求、缓存元数据与KV 数据分开传输

路由器需要知道 KV 在哪里，但不需要让大块 KV 数据经过 Frontend 中转。

  • 请求平面：预处理与定向分发Frontend 校验、应用模板并 tokenize；Router 选 worker，运行时分发 RPC，输出以流式响应返回。
  • 事件平面：更新索引与负载信号worker 发布 KV 增删事件及遥测，Indexer 维护缓存视图。当前默认请求走 TCP、事件走 ZMQ，均可选择 NATS。
  • 发现与 KV 数据路径各司其职运行时按 namespace / component / endpoint 发现服务；本地常用 etcd，K8s 使用资源发现。P/D 的 KV 由后端协调直接传输。
设计含义缓存索引是元数据视图，不是 KV 存储。事件延迟或丢失可能让路由估计与实际命中出现差异。
依据：Architecture · DistributedRuntime / Communication Planes

背景 05 / 时间预算与显存预算

KV 不只是加速缓存，也是并发容量约束

长上下文提高复用收益，也增加常驻状态；命中率高不代表 Decode 没有内存压力。

  • 时间：看任务关键路径上的累计等待排队、未命中 Prefill、KV 搬运、Decode 与工具等待共同构成任务时延；可重叠部分不能简单重复相加。
  • 容量：标准全注意力 KV 的近似式M_KV ≈ 2 × L × H_KV × D × S × b。L 为层数，H_KV 为 KV 头数，D 为头维度，S 为序列长度，b 为每元素字节数；2 对应 K 与 V。
  • 示例：128K 上下文可占 16 GiBL=32、H_KV=8、D=128、b=2、S=131072 时，单序列逻辑 KV 约 16 GiB；四个不共享的序列约 64 GiB。
估算边界不含模型权重、工作区和碎片；TP 分片、前缀共享、量化、滑窗及 MLA 会改变实际每卡占用。
通用 Transformer KV 容量估算；系统取舍参见 Disaggregated Serving · Decode memory tradeoff。

优化 01 / 接入层 已支持 + 应用侧实践

协议归一化与确定性的 Prompt 渲染

API 兼容解决接入；稳定的模板、工具序列与 token 前缀，才是缓存复用的前提。

  • 统一入口，保留工具与推理结构Dynamo 接入 Chat Completions、Responses、Messages；后两者使用类型化内容块，仍需正确的模型模板及工具 / reasoning parser。
  • 固定前缀，增量追加稳定系统提示、tool schema 及顺序，把动态检索结果放到后段；避免时间戳或工具重排让前缀从头失配。
  • 以实际 token 序列验证命中渲染参数、特殊 token、历史思考块剥离都可能改变输入；相同文本语义不保证同一 token 前缀，更不保证相同 KV。
收益减少协议适配摩擦，也为后续路由与缓存复用打好基础。
依据：多协议支持 · 前缀组织为应用侧建议，不代表平台自动改写提示词。

优化 02 / 请求信号 已支持 · 按需启用

Agent Hints：从任务意图到负载估计

nvext.agent_hints 连接 Harness 与调度系统；它是估计与策略信号，不是资源预留协议。

  • osl：预计输出 token 数用于资源估计；启用输出块跟踪后，可结合生成进度对输出块及非共享 prompt 后缀的负载权重衰减，共享前缀仍保留完整权重。
  • priority 与 speculative_prefill前者影响支持该提示的排队 / 后端策略，后者预热下一轮可预测前缀；两者分别优化排队顺序与后续 Prefill。
  • 身份与隔离是独立维度X-Dynamo-Session-ID 标识会话，cache_salt 划分缓存域；不能把会话亲和性当作租户隔离。
实践按任务类型校准 OSL 分布；输出块跟踪需显式启用，不能仅发送 osl 就假设所有负载模型已生效。
依据：NVIDIA Request Extensions · Agent Hints

优化 03 / KV 感知路由 已支持 · 需缓存信息

KV-aware Placement：局部性与负载平衡

根据可复用前缀与预期活跃负载选 worker，而不是仅按连接数或请求数均衡。

  • Indexer：按前缀查询缓存重叠请求被分块、哈希，结合 worker 的 KV 增删事件形成可复用前缀视图；可区分 device / host / disk 等驻留层。
  • 负载跟踪：计入已分配与当前请求活跃 Prefill 工作量、Decode KV 块及可选活跃请求数一起参与代价评估，避免缓存热点吸走全部流量。
  • 选择与调度：两个不同阶段先做候选资格过滤与队列调度，再评分选 worker；缓存命中多不等于一定可以立即接纳。
选择原则综合等待、补算和生成负载，尽量缩短实际响应时间。
依据：KV-Aware Placement · 源码：KV Router

机制展开 / 默认路由代价模型

缓存收益，如何进入worker 评分

用 block-equivalent 工作量表达压力；代价是排序代理，不是毫秒级延迟预测。

普通路径的默认代价结构C = α · max(0, P + I − H) + D + β · R
  • Prefill：未命中部分才需补算P 为已有 Prefill 块，I 为当前输入块，H 为分层缓存加权抵扣；α 对应 prefill_load_scale。
  • Decode：活跃 KV 与批大小压力D 为已有加本次请求的预计活跃块；R 为当前活跃请求数，β 为可选权重，默认 0。
  • 选择：最低代价或带温度采样router_temperature=0 选最低代价，同分随机；非零温度对归一化代价做 softmax 采样。
依据：Cost Calculation · 源码：最低代价与 softmax 选择。实验性条件分离路径存在例外。

优化 04 / 跨层优先级 依赖队列策略与后端配置

跨层调度：优先级、时限与公平性

优先级决定等待次序，队列类别管理流量竞争；两者都不等同于引擎执行抢占。

  • priority / strict_priority 的作用域不同priority 是跨层软优先级，Dynamo 统一数值方向；strict_priority 是支持它的路由等待队列档位，不改变后端优先级。
  • 队列策略决定如何使用提示FCFS / WSPT 支持优先级调整；EDF 按截止时间排序。类别间可用加权 DRR 分配调度额度，减少低优先级饥饿。
  • 后端必须显式开启对应能力SGLang 用 --enable-priority-scheduling，vLLM 用 --scheduling-policy priority；缓存淘汰仍需另行配置。
过载处理配置 busy threshold、队列上限与时限；SLO 是目标，不是保证。必须同时测普通流量尾延迟与拒绝率。
依据：priority 与后端要求 · 路由队列配置

优化 05 / 场景化路由 策略可配置 / 可扩展

按会话结构选择亲和、均衡与容量策略

Dynamo 提供内置 worker-selection 策略与扩展接口；先区分准入约束与评分偏好。

  • 长会话：sticky placement 降低迁移dynamo-sticky-min-load 首轮选低负载节点，后续按会话绑定；绑定后不再按实时负载重选，需注意热点。
  • 并行分支：局部性不能压倒均衡dynamo-two-tier-cost-fn 在明显负载失衡时优先均衡，否则偏向 device KV 命中；阈值应按并发形态校准。
  • 超长输入：容量约束先于评分利用可用 KV、长度估计与准入策略限制并发。定制策略可替换评分 / 选择环节，不应绕过成员发现与负载记账。
扩展路径原文展示 KvRouter Python 接口及 NAT 在线学习案例；当前也有策略 YAML 与 Rust 插件。先 A/B 内置策略，再考虑定制。
依据：场景化路由 · 内置策略 · 源码：策略扩展

优化 06 / 下一轮预热 已支持 · 需显式启用

Speculative Prefill：把准备工作移出关键路径

预热可预测的下一轮前缀，以额外计算换取工具返回后的更低首 token 延迟。

  • 完成当前轮后，渲染预测前缀实现累积当前回复、追加到历史，再通过 formatter / tokenizer 构造下一轮输入；预热请求使用 max_tokens=1。
  • 命中取决于下一轮渲染的一致性工具定义、tool choice、response format 和模板参数需兼容；历史思考块剥离可能改变 token 前缀。
  • 通过资源约束控制投机成本源码限制预处理并发并设置超时 / 取消。评估预热命中率、浪费 token 与前台延迟，避免后台工作反向拖慢请求。
不要混淆这里是提前计算前缀，不是投机解码；也不等同于把远端 KV 自动预取回 GPU。
依据：speculative_prefill · 源码：下一轮预热实现

优化 07 / 分层缓存 依赖引擎与存储集成

分层 KV：容量、带宽与恢复延迟的交换

原文以 HiCache / KVBM 等方案说明多层架构；实际存储层、连接器与回写路径取决于版本和后端。

  • HBM → pinned DRAM → NVMe / 远端下沉释放活跃计算所需显存，但增加恢复 I/O；写穿、按需下沉及共享注册不是所有连接器统一的默认行为。
  • 命中抵扣需要体现层级代价当前路由参考中 host / disk 命中权重默认分别为 0.75 / 0.25；它们是可调评分信用，不是实测速度比例。
  • 以有效带宽和复用概率决定下沉暂停会话可能恢复，也可能结束。关注 offload / reload 字节数、I/O 排队、恢复命中与前台 TTFT，而非只看存储容量。
能力边界四层是参考架构，不是默认全部连通；按返回时间主动预取的通用钩子，原文仍列为演进方向。
依据：分层 KV 架构 · 分层命中权重

优化 08 / 跨节点复用 集成能力 · 非默认保证

共享前缀：从本地命中到远端可加载

将公共前缀的重复 Prefill 转化为 KV 加载，降低多 Agent 首轮冷启动与跨节点迁移成本。

  • 区分“已经持有”与“能够获取”device 命中直接复用；共享层或 peer 命中还需要搬运与加载。当前 kvcr 策略可对 KV fetch hint 候选计入信用。
  • P/D 多轮存在新增 KV 的归属问题本轮 Decode 生成的新 KV 不一定在下轮 Prefill worker 上；共享 / 迁移集成需要同时覆盖初始前缀与新增后缀。
  • 收益条件：搬运成本低于重算成本T_load ≈ 数据量 / 有效带宽 + 固定开销。需计入拓扑、网络拥塞、驻留层与格式兼容，不能按峰值链路带宽推算。
判断门槛加载时间小于重算时间时才值得搬；NIXL 是传输组件，不会自动把所有缓存变成共享池。
依据：共享 KV · 共享层与 kvcr 信用 · 源码：共享命中描述

机制展开 / 复用的正确性条件

缓存命中不等于任意块都能复用

标准前缀缓存复用要求连续的上下文链；相同后缀 token 在不同前文下通常产生不同 KV。

  • 块身份包含前缀关系请求按块构建哈希 / 前缀索引，不能把“相同 token 的局部片段”直接当作独立 KV 对象来拼接。
  • 连续可加载量比总命中量更重要SharedCacheHits::loadable_beyond() 从本地前缀末端向后延伸，遇到缺口停止，并考虑最小加载块数。
  • 复用域还需满足模型与租户约束模型权重、位置 / 模板语义、KV 布局与后端支持需兼容。cache_salt 划分缓存域，但不替代认证授权。
指标拆分区分索引命中、连续可加载、实际加载成功与最终 Prefill 节省；不要用一个“命中率”掩盖整条链路。
源码：SharedCacheHits · Cache salt 与后端隔离边界

优化 09 / 按价值保留 部分支持 · 细粒度接口演进中

缓存保留：从 LRU 到复用价值

淘汰策略应考虑下一次复用概率与重算代价，而不只考虑最近访问时间。

  • 目标：单位容量的预期计算节省可用“复用概率 × 避免的重算成本 / 占用字节”理解保留价值；这是评估思路，不是 Dynamo 默认淘汰公式。
  • 现有路径：请求级 priority 透传SGLang 需配置 --radix-eviction-policy priority 才启用对应缓存淘汰；调度优先级与缓存优先级不是自动等价。
  • 引擎原语 ≠ 统一的跨层接口TRT-LLM 有 token-range retention 原语，但当前 Dynamo 透传 priority 不支持其优先级淘汰；TTL / 区间保留仍需区分接口层次。
明确限制不要把 nvext.cache_control 当成可用的 TTL 锁定接口；当前不是这套语义。
依据：Selective Cache Retention · 当前后端支持边界

优化 10 / 生命周期感知 跨层控制仍属探索 / 集成方向

会话生命周期与临时 KV 的回收

将 spawn、pause、resume、terminate 和 compaction 事件映射为缓存保留与回收意图。

  • 终止与压缩产生 ephemeral KV短命子 Agent 的私有历史、compaction 前的旧历史可能不再引用；可降低保留优先级，并避免无收益的跨层写入。
  • 回收要区分私有后缀与共享前缀同一前缀可能服务多个会话；需要引用 / 所有权信息，不能按 session 结束事件直接删除全部相关块。
  • 语义检测必须服从真实输入thinking token 只有在后续模板不再使用时才是临时状态；删除仍需参与 attention 的历史会改变模型行为。
演进方向将会话事件与缓存保留、淘汰、下沉连接起来；已有会话标识或亲和性不等于生命周期回收。
依据：Agent Lifecycle Awareness

优化 11 / 分离 Prefill 与 Decode 已支持 · 按负载选择

P/D 分离：隔离干扰与独立容量规划

Prefill 更偏计算密集，Decode 常受内存带宽与 KV 容量影响；最优配置取决于模型、批大小和硬件。

  • 避免长 Prefill 干扰 Decode 迭代聚合引擎可用 chunked prefill 平衡干扰；独立 P 池进一步隔离长输入，P / D 可分别选择 batch、TP 和副本数。
  • 显式承担 KV 传输与池化开销Prefill 返回传输元数据，Decode 协调 KV 加载后生成；NIXL 提供高效数据路径，但链路与调度开销仍需计入 TTFT。
  • 缓存命中率会改变最佳 P:D 比例高命中减少有效 Prefill，却不等比例减少 Decode KV 容量；固定 GPU 预算下扩 P 池可能挤压 D 池并发。
取舍低并发、短输入或高缓存命中时，聚合部署可能更划算；不要为“分离”而分离。
补充依据：Disaggregated Serving · 部署示例

优化 12 / 资源弹性 Planner 已支持 · 需指标与配置

Planner：预测容量 + 运行时反馈

围绕 TTFT / ITL 服务目标调整推理图，而不是直接以 GPU 利用率作为唯一扩缩容信号。

  • Throughput-based：预测所需容量流量预测结合引擎性能模型估计满足 TTFT / ITL 的副本数；模型可来自 profiling、worker 自测或性能估算。
  • Load-based：根据 FPM 反应式调整消费 ForwardPassMetrics；SLA 目标下用在线回归，其他目标可用队列 / KV 阈值。该模式不要求 KV Router 或离线 profiling。
  • 组合使用，处理突发与冷启动SLA 模式下预测容量可作为下界，负载反馈做实时调整；规划时仍需考虑模型加载、热缓存损失与缩容排空。
边界Planner 主要优化推理服务指标；成功率、工具等待和完整任务时间仍要由应用侧联合评估。
补充依据与源码入口：Dynamo Planner · SLA-driven autoscaling
